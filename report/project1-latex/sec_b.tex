\section{Experimental study}\label{sec:experiments}
We report the numbers that carry each paper's argument, then ask whether the experiments are sufficient for the claims. Verdicts use the symbols of Table~\ref{tab:coverage}: \yes\ supported, \half\ directional or conditional, \no\ not shown.

\subsection{Setup, datasets and metrics}
\paragraph{Setup.} Table~\ref{tab:glance} lines up the four studies. Three ran on 8-core, 32\,GB machines; CODDTest's efficiency study used 64 cores and 512\,GB. Budgets, DBMS versions and baselines all differ, so we compare numbers only within a study.

\paragraph{Datasets.} No study uses a fixed benchmark. All four generate small random databases and workloads, which suits short counterexamples. WriteCheck also builds a historical set: 140 transaction bugs from 2018 to 2022, of which 35 leave a wrong state and 32 violate WSS~\cite{writecheck}. Figure~\ref{fig:trigger} shows how small those 32 are. All need at most two tables and five transactions, 97\% of their tables hold at most five rows, and 72\% need a specific key, index or column constraint. This justifies small generated states for this bug class; it says nothing about larger ones, and no paper varies database size.

\paragraph{Metrics and methodology.} \emph{Detection} is counted in unique confirmed bugs, which depend on reduction and developer judgment. \emph{Cost} is tests or queries per unit time. \emph{Diversity} is unique query plans or code coverage. The comparisons with earlier tools come in two kinds, and the difference matters for everything below. A \textbf{capability study} asks whether each tool could expose a set of known bugs. A \textbf{fresh run} lets every tool generate its own tests for a fixed time. All four papers report single runs per setting, with no confidence intervals.

\subsection{CODDTest results}
CODDTest found 45 new bugs in five DBMSs, 24 of them logic bugs (19 fixed). A manual analysis finds 11 of the 24 in features earlier oracles do not test, such as subqueries, ON clauses and CASE~\cite[Table~2]{coddtest}.

\begin{figure}[!tb]
\centering\includegraphics[width=\columnwidth]{fig4}
\caption{\textbf{Fewer tests, far more plans.} Tests run against unique plans reached in 24 hours on SQLite 3.42.0.0, one point per configuration, from \cite[Table~3]{coddtest}. Branch coverage is 62--64\% for all but DQE (46.7\%).}
\label{fig:efficiency}
\end{figure}

Figure~\ref{fig:efficiency} shows the trade-off. CODDTest completes 4.2 times fewer tests than NoREC, because each test needs at least three queries, yet reaches about 15 times more unique plans, while branch coverage hardly moves. Subqueries open the plan space: folding only expressions finishes the most tests and reaches the fewest plans. Figure~\ref{fig:depth} shows the depth sweep. Deeper expressions cost more and finish fewer tests, and the plans seen fall with them. The sweep measures cost, not bugs.

\begin{figure}[!tb]
\centering\includegraphics[width=\columnwidth]{fig_depth}
\caption{\textbf{Deeper expressions cost more and explore less.} Expression-only configuration, one 24-hour run per depth, indexed to depth 1. Curves read off \cite[Figs.~2 and~3]{coddtest} (approximate); end labels use the paper's reported values.}
\label{fig:depth}
\end{figure}

In a fresh 24-hour run on SQLite 3.30.0, an old release in which NoREC and TLP had already found 31 bugs, CODDTest finds 25 unique bugs against 27 each for NoREC and TLP, but the most that no other oracle found (Table~\ref{tab:fresh}).

\begin{verdicts}
\verdict{\yes}{New logic bugs in mature systems.}{24 confirmed, spread over five DBMSs.}
\verdict{\half}{Reaches bugs other oracles miss.}{11 of 24, but measured on its own bugs (Figure~\ref{fig:homeset}); the fresh run shows complementarity, not superiority.}
\verdict{\no}{Deep expressions do not pay off.}{The sweep measures cost, not bug yield.}
\end{verdicts}

\subsection{DDLCheck results}
DDLCheck submitted 34 bugs; 29 were confirmed as new, 21 of them schema-related logic bugs, with no false positives~\cite[Table~2]{ddlcheck}. Seven of the 21 never changed a query result: four corrupted stored data and three the schema. SELECT revealed 23 of the 29 confirmed bugs, and CREATE, ALTER, INSERT or REPLACE the other six~\cite[Fig.~6]{ddlcheck}, which are out of reach for any query-only comparison. In the capability study NoREC exposes none of the 21 schema bugs. The ablation keeps only sequences whose schema structure is new, and yields 8 unique bugs against 5 for random selection (Figure~\ref{fig:ablation}b); a stricter variant logs as many raw failures but only 4 unique bugs.

\begin{verdicts}
\verdict{\yes}{Schema history exposes bugs query oracles miss.}{29 confirmed, none false, 7 invisible to queries.}
\verdict{\half}{The diversity filter helps.}{8 against 5 bugs in one 24-hour run per DBMS.}
\verdict{\no}{PostgreSQL and SQLite are clean.}{Zero findings in a bounded search is not evidence of absence.}
\end{verdicts}

\subsection{Radar results}
Ten rounds produced 1,663 reports, which three weeks of reduction turned into 42 submitted bugs: 38 confirmed (30 metadata-related), one duplicate and three false positives~\cite[Sec.~4.2]{radar}. TiDB accounts for 31 of the 42 and 24 of the 30 metadata bugs~\cite[Table~2]{radar}. The guidance ablation (Figure~\ref{fig:ablation}a) is the clearest curve in the four papers: on TiDB the gap opens within two hours and ends at 19 against 12. Across all five DBMSs the totals are 22 against 14, so most of the effect is TiDB. Function coverage barely moves (20.3\% against 19.7\% on MySQL), another case where coverage hides what bug counts show. In the fresh 12-hour run, all tools together find 21 metadata bugs, and Radar finds 20, 15 of them alone.

\begin{figure}[!tb]
\centering\includegraphics[width=\columnwidth]{fig_ablation}
\caption{\textbf{Design choices help, by small margins.} (a) Radar on TiDB, cumulative unique bugs with and without metadata guidance, read off \cite[Fig.~7]{radar} (approximate). (b) Every with/without pair reported, from \cite[Table~3]{ddlcheck} and \cite[Table~3]{radar}. One run each.}
\label{fig:ablation}
\end{figure}

\begin{verdicts}
\verdict{\yes}{Raw copies expose metadata bugs others miss.}{15 of 21 in a fresh run were Radar's alone.}
\verdict{\half}{Guidance helps.}{22 against 14 in one 12-hour run, mostly on TiDB.}
\verdict{\half}{The method generalizes across DBMSs.}{24 of 30 metadata bugs come from one system.}
\end{verdicts}

\subsection{WriteCheck results}
WriteCheck's argument starts before any testing: 32 of the 35 historical critical bugs (91.4\%) violate WSS, and 29 of those 32 trigger when statements run in a fixed order, which justifies controlling statement order. In discovery, 101 violations group into 22 unique cases; 13 were confirmed critical bugs (11 new) and 9 were false positives. The tool comparison uses a \emph{different} set of 29 bugs: 13 found by WriteCheck plus 16 found earlier by DT\textsuperscript{2}, Troc and TxCheck~\cite[Sec.~6.5.1]{writecheck}. WriteCheck exposes all 29, the others at most 23 (Figure~\ref{fig:homeset}). With more than half of the set coming from competitors, this is the fairest capability study of the four. In the fresh 12-hour run, WriteCheck finds 4 critical bugs and the others 1 or 2, although they also find non-critical bugs WriteCheck cannot.

\section{Cross-study discussion and threats to validity}\label{sec:discussion}
Across the four papers, claims that a bug exists hold up, and claims about how many bugs a tool finds relative to others do not. Two reporting habits explain most of the gap, and both are easy to miss when reading one paper at a time.

\begin{figure*}[!tb]
\centering\includegraphics[width=\linewidth]{fig_homeset}
\caption{\textbf{Every capability study plays on home turf.} Each panel takes one paper's bug set and shows the share each tool can expose, as judged by that paper's authors. In the first three the set is the reviewed tool's own bugs, so it scores 100\% by construction; WriteCheck's set mixes 13 own bugs with 16 found by the other tools. From \cite[Table~2]{coddtest}, \cite[Table~4]{ddlcheck}, \cite[Table~5]{radar}, \cite[Table~3]{writecheck}.}
\label{fig:homeset}
\end{figure*}

\paragraph{Pattern 1: the home-set effect.} Three of the four capability studies ask how many of the \emph{new tool's own} bugs older tools could have found (Figure~\ref{fig:homeset}). The new tool wins by construction, and the baselines can only lose. The design does show that the new oracle reaches bugs the old ones cannot, but it cannot show the reverse. Only CODDTest's fresh SQLite run looks the other way, and there CODDTest misses 14 bugs that the other oracles found.

\paragraph{Pattern 2: headline counts sit at different stages.} Figure~\ref{fig:units} draws every reported bug as a square. Each abstract leads with the row total, but the totals hold different things. All 45 of CODDTest's bugs are confirmed. Of WriteCheck's 22, nine are false positives and two were already known. Adding or ranking the headline numbers mixes stages; confirmation counts are snapshots at publication, and overlap between campaigns is unknown.

\begin{figure}[!tb]
\centering\includegraphics[width=\columnwidth]{fig_units}
\caption{\textbf{What the headline numbers contain.} One square per reported bug; the row total is the number each abstract leads with. From \cite[Table~1]{coddtest}, \cite[Table~2]{ddlcheck}, \cite[Table~2]{radar}, \cite[Table~2]{writecheck}.}
\label{fig:units}
\end{figure}

\paragraph{Pattern 3: triage cost goes unmeasured.} Every reported bug starts as a pile of raw reports that someone reduces and deduplicates. Figure~\ref{fig:triage} puts the numbers the papers do give on one scale. In CODDTest's SQLite run, NoREC and TLP produced over 3,500 reports per unique bug, CODDTest about 280 and EET under 3. Radar needed 40 per bug and three weeks of manual work; WriteCheck about 5. The spread covers three orders of magnitude, yet no paper treats triage effort as a metric, and none reports the hours behind its counts except Radar. An oracle that finds one more bug at a hundred times the reports may be worse in practice.

\paragraph{Threats to validity.} \emph{Internal:} a broken precondition (nondeterminism, type conversion, an incomplete rebuild) can produce a mismatch without a defect, and reduction can change the plan, so reduced cases need re-checking. \emph{Construct:} a unique plan is not a unique semantic path, and high coverage coexists with undetected faults; SQLite reaches full branch coverage with its own suite and still has logic bugs~\cite[Sec.~4.3]{coddtest}. \emph{External:} deployments differ even for one system (single-node CockroachDB for WriteCheck, three nodes for Radar), and small generated states do not cover long production histories. Figure~\ref{fig:dbms} shows where the target bugs come from. Only CODDTest spreads its findings evenly; DDLCheck's cluster in MySQL, and Radar's and WriteCheck's in TiDB. That may reflect each tool's fit to a dialect, the effort spent per system, or a system's maturity, and the papers do not separate these explanations, so the grid says nothing about which DBMS is more reliable.

\paragraph{What stronger evidence would look like.} Pin shared DBMS revisions. Build capability sets from bugs no compared tool found. Repeat randomized runs with recorded seeds and report the spread. Measure triage time, and add negative controls (valid cases that look inconsistent) to measure precision directly.

\begin{takeaway}
Each oracle finds real bugs the others miss. None of the papers shows by how much, because no experiment compares the tools on neutral ground.
\end{takeaway}

\section{Conclusions and research directions}\label{sec:conclusions}
Read together, the four papers suggest building a test campaign around independent sources of disagreement: CODDTest for expressions, DDLCheck for schema history, Radar for metadata, WriteCheck for write interleavings, with verdicts kept separate so each failure stays attributable. Composing them needs its own argument. An evolved schema from DDLCheck would give CODDTest an interesting starting state, but only once the state is confirmed to be built as intended, and dropping a constraint before a WriteCheck run changes conflict behavior and can invalidate the serial reference.

\Needspace{6\baselineskip}\paragraph{Open questions.}
\begin{enumerate}[leftmargin=1.3em,itemsep=1pt,topsep=2pt]
\item \textbf{What should guide the generator?} The depth sweep, DDLCheck's filter and Radar's guidance agree that syntactic size is a poor target and that novel schema structure or metadata pays off.
\item \textbf{How can triage get cheaper?} Isolation-level names do not pin down write semantics, and a raw Radar campaign needs weeks of reduction. Per-dialect profiles of valid transformations could cut both.
\item \textbf{What about faults on both paths?} Every reference here runs on the system under test, and agreement across finitely many checks cannot certify correctness.
\end{enumerate}

\paragraph{A neutral-ground experiment.} The missing evidence could come from one shared protocol. Fix a set of DBMS revisions. Seed a bug set from fixed historical reports that none of the compared tools found, as WriteCheck partly did. Run every tool for the same budget, several times with recorded seeds, and report unique bugs with their spread, false positives and raw reports per bug. Score each oracle only inside the failure classes it claims (Table~\ref{tab:coverage}), so that a transaction oracle is never penalized for missing an optimizer bug. Such a benchmark would turn today's existence claims into comparable rates.

\paragraph{Conclusion.} Each of the four oracles makes a new part of database behavior testable by comparing two runs that must agree, and each holds only under its precondition: a stable value for folding, a preserved definition for rebuilding, a query whose meaning survives the dropped metadata, and a conflict model that justifies the serial order. Within those conditions, the evidence that each oracle finds real, otherwise-missed bugs is strong. The evidence for ranking them does not exist yet, and an experiment designed to provide it is the most useful next step for the field.
