\section{Experimental study}\label{sec:experiments}
This section reviews the experiments reported in the four papers. For each paper we summarize the results that carry its argument and then assess whether the experiments are sufficient for the claims made. The verdicts use the symbols of Table~\ref{tab:coverage}: \yes\ means the claim is supported, \half\ that the evidence is directional or holds only under conditions, and \no\ that the experiments do not show it.

\subsection{Setup, datasets and metrics}
\paragraph{Setup.} Table~\ref{tab:glance} compares the four experimental setups. Three studies used machines with 8 cores and 32\,GB of memory, while CODDTest's efficiency study used a server with 64 cores and 512\,GB. Because budgets, DBMS versions and baselines also differ, we compare results only within a study.

\paragraph{Datasets.} None of the studies uses a fixed benchmark dataset. All four generate small random databases and workloads, which suits the goal of producing short counterexamples. WriteCheck additionally studies 140 transaction bugs reported between 2018 and 2022, of which 35 leave the database in a wrong state and 32 violate WSS~\cite{writecheck}. These 32 cases are small~\cite[Fig.~2]{writecheck}: all of them need at most two tables and five transactions, 97\% of their tables hold at most five rows, and 72\% depend on a specific key, index or column constraint. These figures justify small generated states for transaction bugs. They say nothing about larger databases, and none of the four papers varies the database size.


\paragraph{Metrics and methodology.} The papers measure detection as unique confirmed bugs, cost as tests per unit of time, and diversity as unique query plans or code coverage. Their comparisons with earlier tools fall into two kinds, and the distinction matters for the rest of this section. A \textbf{capability study} takes a set of known bugs and asks whether each tool could expose them. A \textbf{fresh run} lets every tool generate its own tests for the same amount of time and counts what each one finds. All four papers report a single run per configuration and give no confidence intervals.

\subsection{CODDTest results}
CODDTest found 45 previously unknown bugs in five DBMSs. Twenty-four of them are logic bugs, of which 19 had been fixed at publication time. A manual analysis by the authors concludes that 11 of the 24 lie in features that earlier oracles do not test, such as subqueries, ON clauses and CASE expressions~\cite[Table~2]{coddtest}.

\begin{figure}[!tb]
\centering\includegraphics[width=\columnwidth]{fig4}
\caption{\textbf{Tests run and unique query plans reached in 24 hours} on SQLite 3.42.0.0, one point per oracle configuration, from \cite[Table~3]{coddtest}. Branch coverage is 62--64\% for all configurations except DQE (46.7\%).}
\label{fig:efficiency}
\end{figure}

Figure~\ref{fig:efficiency} shows the efficiency results. CODDTest completes 4.2 times fewer tests than NoREC in the same time, because each test needs at least three queries, but it reaches about 15 times more unique query plans. Branch coverage is almost the same for all of them and would miss this difference. The variants show that subqueries supply most of the extra plans, since folding only expressions completes the most tests but reaches the fewest plans. Figure~\ref{fig:depth} shows what happens when the maximum expression depth grows from 1 to 15. Each query becomes slower, fewer tests complete, and fewer unique plans are reached. The sweep therefore measures cost; it does not measure how many bugs deeper expressions find.

\begin{figure}[!tb]
\centering\includegraphics[width=\columnwidth]{fig_depth}
\caption{\textbf{Cost of the CODDTest expression-only configuration as the maximum depth grows,} one 24-hour run per depth, relative to depth 1. Curves read off \cite[Figs.~2 and~3]{coddtest} (approximate); end labels use the values reported in the paper.}
\label{fig:depth}
\end{figure}

In a fresh 24-hour run on SQLite 3.30.0, an older release in which NoREC and TLP had already found 31 bugs, CODDTest found 25 unique bugs, slightly fewer than the 27 found by each of NoREC and TLP. It did, however, find the largest number of bugs that no other oracle found (Table~\ref{tab:fresh}).

\begin{verdicts}
\verdict{\yes}{CODDTest finds new logic bugs in mature systems.}{24 were confirmed, spread over five DBMSs.}
\verdict{\half}{It reaches bugs that other oracles miss.}{The 11 of 24 are measured on its own bugs (Figure~\ref{fig:homeset}); the fresh run shows complementarity, not superiority.}
\verdict{\no}{Deep expressions are not worth generating.}{The depth sweep measures cost only, not the number of bugs found.}
\end{verdicts}

\subsection{DDLCheck results}
DDLCheck submitted 34 bugs, and 29 were confirmed as previously unknown; 21 of these are schema-related logic bugs, and none of the submissions was a false positive~\cite[Table~2]{ddlcheck}. Seven of the 21 logic bugs never changed a query result: four corrupted stored data and three corrupted the schema. A SELECT statement revealed 23 of the 29 confirmed bugs, while CREATE, ALTER, INSERT or REPLACE statements revealed the remaining six~\cite[Fig.~6]{ddlcheck}, which no oracle that compares only query results could have detected. In the capability study, NoREC could expose none of the 21 schema bugs. The ablation evaluates DDLCheck's filter, which keeps only DDL sequences whose resulting schema structure has not been seen before. With the filter, DDLCheck found 8 unique bugs, against 5 with random selection (Figure~\ref{fig:ablation}b). A stricter variant produced as many raw failures as the original but only 4 unique bugs.

\begin{verdicts}
\verdict{\yes}{Schema history exposes bugs that query oracles miss.}{29 confirmed, no false positives, 7 invisible to queries.}
\verdict{\half}{The diversity filter improves detection.}{8 against 5 bugs, from one 24-hour run per DBMS.}
\verdict{\no}{PostgreSQL and SQLite are free of schema bugs.}{Finding nothing in a bounded search is not evidence of absence.}
\end{verdicts}

\subsection{Radar results}
Radar's ten testing rounds produced 1,663 reports. After about three weeks of reduction, the authors submitted 42 unique bugs, of which 38 were confirmed (30 of them metadata-related), one was a duplicate and three were false positives~\cite[Sec.~4.2]{radar}. The findings are concentrated in one system: TiDB accounts for 31 of the 42 submissions and for 24 of the 30 metadata bugs~\cite[Table~2]{radar}. The ablation of the guidance strategy (Figure~\ref{fig:ablation}a) gives the clearest single result in the four papers. On TiDB, guided Radar pulls ahead within the first two hours and ends with 19 unique bugs against 12 without guidance. Across all five DBMSs the totals are 22 against 14, so most of the effect comes from TiDB. Function coverage on MySQL barely changes (20.3\% against 19.7\%). In the fresh 12-hour run, all tools together found 21 metadata bugs; Radar found 20 of them, and 15 of those were found by no other tool.

\centering\includegraphics[width=\columnwidth]{fig_ablation}
\caption{\textbf{Ablation results reported by DDLCheck and Radar.} (a) Radar on TiDB: cumulative unique bugs with and without metadata guidance, read off \cite[Fig.~7]{radar} (approximate). (b) Unique bugs with and without each design choice, from \cite[Table~3]{ddlcheck} and \cite[Table~3]{radar}. Each value comes from a single run.}
\label{fig:ablation}
\end{figure}

\begin{verdicts}
\verdict{\yes}{Raw database copies expose metadata bugs that other oracles miss.}{15 of the 21 metadata bugs in the fresh run were found only by Radar.}
\verdict{\half}{Guidance improves detection.}{22 against 14 bugs, from one run and mostly on TiDB.}
\verdict{\half}{The method generalizes across DBMSs.}{24 of the 30 metadata bugs come from a single system.}
\end{verdicts}

\subsection{WriteCheck results}
WriteCheck grounds its design in the historical study. Of the 35 critical bugs, 32 (91.4\%) violate WSS, and 29 of those 32 can be triggered by executing the statements in a fixed order, which justifies controlling statement order. In discovery, its 101 flagged violations reduce to 22 unique cases: 13 confirmed critical bugs (11 new) and 9 false positives. The comparison with other tools uses a different set of 29 bugs, despite the identical count: it combines the 13 bugs found by WriteCheck with 16 found earlier by DT\textsuperscript{2}, Troc and TxCheck~\cite[Sec.~6.5.1]{writecheck}. WriteCheck exposes all 29, and the other tools at most 23 (Figure~\ref{fig:homeset}). Since most of this set comes from the competing tools, it is the fairest of the four capability studies. In the fresh 12-hour run, WriteCheck found 4 critical bugs and the other tools 1 or 2 each, although they also found non-critical bugs outside WriteCheck's scope.

\section{Cross-study discussion and threats to validity}\label{sec:discussion}
Taken together, the four papers convincingly show that each method finds real bugs, but they do not show how many more bugs one method finds than another. Three reporting practices explain most of this gap. Each is easy to overlook when a paper is read on its own.

\begin{figure*}[!tb]
\centering\includegraphics[width=\linewidth]{fig_homeset}
\caption{\textbf{Capability studies on known bugs.} Each panel takes one paper's bug set and shows the share that each tool can expose, as judged by that paper's authors. In the first three panels the set consists of the reviewed tool's own bugs, so that tool scores 100\% by construction. WriteCheck's set combines its own 13 bugs with 16 found by the other tools. From \cite[Table~2]{coddtest}, \cite[Table~4]{ddlcheck}, \cite[Table~5]{radar} and \cite[Table~3]{writecheck}.}
\label{fig:homeset}
\end{figure*}

\paragraph{Capability is measured on the new tool's own bugs.} Three of the four capability studies ask how many of the new tool's bugs the older tools could have found (Figure~\ref{fig:homeset}). Under this design the new tool reaches 100\% by construction, and the baselines can only score lower. The studies do establish that the new oracle reaches bugs the older ones cannot, but they cannot reveal what the new oracle misses. Only CODDTest's fresh SQLite run provides evidence in that direction, and in that run CODDTest missed 14 bugs that the other oracles found.

\paragraph{Headline counts refer to different stages.} Figure~\ref{fig:units} draws each reported bug as a square. Every abstract leads with the total of its row, but the totals contain different things. All 45 of CODDTest's bugs were confirmed, whereas 9 of WriteCheck's 22 violations are false positives and 2 were already known. Adding or ranking these numbers would therefore mix reporting stages. In addition, confirmation counts are snapshots taken at publication, and the overlap between the four campaigns is unknown.

\begin{figure}[!tb]
\centering\includegraphics[width=\columnwidth]{fig_units}
\caption{\textbf{Composition of each paper's headline bug count.} One square per reported bug; the row total is the number each abstract reports. From \cite[Table~1]{coddtest}, \cite[Table~2]{ddlcheck}, \cite[Table~2]{radar} and \cite[Table~2]{writecheck}.}
\label{fig:units}
\end{figure}

\paragraph{The cost of triage is not measured.} Every unique bug starts as a set of raw reports that someone has to reduce and deduplicate. Figure~\ref{fig:triage} places the counts that the papers do report on a common scale. In CODDTest's SQLite run, NoREC and TLP produced more than 3,500 reports per unique bug, CODDTest about 280 and EET fewer than 3. Radar needed about 40 reports per bug and three weeks of manual work, and WriteCheck about 5. These ratios span three orders of magnitude, yet no paper treats triage effort as a metric, and only Radar reports how long it took. An oracle that finds one more bug but produces a hundred times as many reports may be less useful in practice.

\paragraph{Threats to validity.} The main threat to internal validity is a violated precondition: nondeterminism, implicit type conversion or an incomplete schema recreation can produce a mismatch without a defect. Construct validity is limited because a unique query plan does not imply a unique semantic path and because high coverage can coexist with undetected faults; SQLite reaches full branch coverage with its own test suite and still contains logic bugs~\cite[Sec.~4.3]{coddtest}. External validity is limited because deployments differ even for one system (WriteCheck tests a single-node CockroachDB, Radar a three-node cluster), because small generated states do not represent long production histories, and because of where the bugs were found. Figure~\ref{fig:dbms} shows that only CODDTest's findings are spread evenly across systems; DDLCheck's are concentrated in MySQL, and Radar's and WriteCheck's in TiDB. The papers do not separate possible causes such as dialect fit, effort per system or system maturity, so the distribution says nothing about which DBMS is more reliable.

\section{Conclusions and research directions}\label{sec:conclusions}
The four papers suggest organizing database testing around several independent sources of disagreement: CODDTest for expression evaluation, DDLCheck for schema history, Radar for metadata and WriteCheck for concurrent writes. Their verdicts should be kept separate so that each failure can be attributed to one relation, and any combination of them, such as running CODDTest on a schema produced by DDLCheck, needs its own validity argument.

\Needspace{6\baselineskip}\paragraph{Open questions.}
\begin{enumerate}[leftmargin=1.3em,itemsep=1pt,topsep=2pt]
\item \textbf{What should guide test generation?} The depth sweep, DDLCheck's filter and Radar's guidance all indicate that syntactic size is a poor target and that new combinations of schema structure or metadata are more productive.
\item \textbf{How can triage be made cheaper?} Isolation-level names do not fully determine write semantics, and a raw Radar campaign needs weeks of reduction. Per-dialect profiles of valid transformations could reduce both problems.
\item \textbf{How can faults that affect both executions be found?} Every reference execution reviewed here runs on the system under test, and agreement across a finite set of checks cannot prove correctness.
\end{enumerate}

\paragraph{A neutral comparison.} The missing comparative evidence could come from a shared experimental protocol. Such a protocol would fix a set of DBMS revisions and seed a bug set from historical reports that none of the compared tools found, as WriteCheck partly did. Every tool would run with the same budget, several times and with recorded seeds, and the results would report unique bugs with their spread, false positives and raw reports per bug. It would also measure triage time and include negative controls, valid cases that look inconsistent, to measure precision. Each oracle would be scored only within the failure classes it claims to cover (Table~\ref{tab:coverage}), so that a transaction oracle is not penalized for missing an optimizer bug.

\paragraph{Conclusion.} Each of the four methods makes a new part of database behavior testable by comparing two executions that must agree, and each comparison is valid only under its precondition: folding needs a stable value, recreation needs a preserved definition, metadata removal needs a query whose meaning does not depend on the metadata, and serial replay needs a conflict model that justifies the chosen order. Under those conditions, the evidence that each method finds real bugs missed by earlier oracles is strong. Evidence for ranking the methods against each other does not yet exist, and an experiment designed to provide it would be the most useful next step.
