\section{Experimental study}\label{sec:experiments}

This section examines the experiments the original authors ran. For each paper we give the numbers that carry its argument, then ask whether the experiments are sufficient for the claims. Each verdict uses the symbols of Table~\ref{tab:coverage}: \yes\ supported, \half\ directional or conditional, \no\ not shown.

\subsection{Experimental setup and comparability}
Table~\ref{tab:glance} lines up the four setups. Three studies ran on 8-core machines with 32\,GB of memory; CODDTest's efficiency study used a 64-core server with 512\,GB. Budgets range from single 12-hour runs to ten rounds of 24 hours, the DBMS versions differ, and each paper picks its own baselines. A raw comparison across rows would mostly measure these differences. We therefore compare numbers only within a study and keep each paper's own denominators.

\subsection{Datasets and generated workloads}
None of the studies uses a fixed benchmark dataset. Three generate small random databases and workloads, which suits the aim of exploring combinations of types, NULLs, constraints and interleavings and of producing short counterexamples. The fourth, WriteCheck, also builds a historical dataset: 140 transaction bugs reported between January 2018 and December 2022, of which 35 leave the database in a wrong state~\cite{writecheck}. The two kinds of evidence answer different questions. Generated workloads test whether an oracle discovers failures on its own; historical bugs test whether it recognizes known ones.

Table~\ref{tab:trigger} shows what the 35 historical cases look like. Nearly all use one table, most involve two transactions, and most hold a handful of rows. This supports WriteCheck's choice of small generated states for this bug class. It says nothing about larger states or longer histories, and no paper varies database size, so none can say how its oracle behaves as data grows.

\subsection{Metrics and methodology}
The papers measure three things in different units, and we keep the units apart.
\emph{Detection} is counted in unique confirmed bugs, which depend on reduction, deduplication and developer judgment.
\emph{Cost} is counted in tests or queries per unit time; one test can issue several queries, so the two units do not convert.
\emph{Diversity} is counted in unique query plans, unique schema structures, or code coverage, and similar coverage can coexist with very different bug yields.
False positives measure how much triage an oracle demands. Throughout, we separate a submitted mismatch from a developer-confirmed defect.

The comparisons with earlier tools come in two kinds, and the distinction matters for everything that follows. A \textbf{capability study} takes a set of known bugs and asks whether each tool could expose them, by replaying the bug's test case or by reasoning about the tool's design. A \textbf{fresh run} lets each tool generate its own tests for a fixed time and counts what it finds. Capability says what an oracle can recognize; a fresh run says what it actually discovers. All four papers report single runs per setting, without confidence intervals. Radar ran ten discovery rounds and WriteCheck five, but neither reports how much the results varied between rounds.

\subsection{CODDTest results}
CODDTest reports 45 previously unknown bugs in five DBMSs: 24 logic bugs, 14 internal errors, 2 crashes and 5 hangs. Of the 24 logic bugs, 19 were fixed and 5 verified by publication~\cite{coddtest}. A manual analysis finds that 11 of the 24 lie in features the earlier oracles do not test: subqueries, ON clauses, CASE and ANY expressions, AVG and INSERT statements~\cite[Table~2]{coddtest}.

\begin{figure}[!tb]
\centering\includegraphics[width=\columnwidth]{fig4}
\caption{\textbf{Tests run against unique plans reached in 24 hours, one point per oracle configuration} (SQLite 3.42.0.0, 10 threads). Values from \cite[Table~3]{coddtest}. Plan counts and branch coverage come from separate runs with the same configuration. Coverage is 62--64\% for every configuration except DQE (46.7\%).}
\label{fig:efficiency}
\end{figure}

Figure~\ref{fig:efficiency} shows the efficiency trade-off. CODDTest completes 4.2 times fewer tests than NoREC in the same 24 hours, because each test needs at least three queries, yet it reaches about 15 times more unique query plans. Branch coverage hardly separates the oracles, so coverage alone would hide the difference. The variants tell the same story from inside CODDTest: folding only expressions finishes the most tests but reaches the fewest plans, and subqueries are what open the plan space.

\begin{figure}[!tb]
\centering\includegraphics[width=\columnwidth]{fig_depth}
\caption{\textbf{CODDTest expression-depth sweep,} expression-only configuration, one 24-hour run per setting. Re-plot of \cite[Figs.~2 and~3]{coddtest} from values read off the published figures; values are approximate.}
\label{fig:depth}
\end{figure}

Figure~\ref{fig:depth} raises the maximum expression depth from 1 to 15. Time per query grows almost tenfold and completed tests fall by 89\%. Unique plans fall too, which looks odd until one notices that fewer completed tests means fewer plans seen in a fixed window; the sweep does not report plans per test. Read together, the panels say that deeper expressions are expensive under a fixed budget. They do not say that deep expressions never find bugs. The authors add that most reduced bug cases are shallow, but reduction strips exactly the structure that may have helped the generator find the bug.

The third experiment is a fresh run on SQLite 3.30.0, an old release in which NoREC and TLP had already found 31 bugs (Table~\ref{tab:fresh}). CODDTest finds 25 unique bugs against 27 each for NoREC and TLP, but the most bugs that no other oracle found, 4 against 3, 2 and 3.

\begin{verdicts}
\verdict{\yes}{New logic bugs in mature systems.}{24 confirmed, spread over five DBMSs.}
\verdict{\half}{Bugs that other oracles miss.}{11 of 24 in the manual analysis, but measured on CODDTest's own bugs (Figure~\ref{fig:homeset}). The fresh run shows complementarity (4 exclusive), not superiority (25 against 27).}
\verdict{\half}{More plans per unit of work.}{A 15-fold gap is large, but it comes from one run per oracle.}
\verdict{\no}{Deep expressions do not pay off.}{The depth sweep measures cost, not bug yield.}
\end{verdicts}

\subsection{DDLCheck results}
DDLCheck submitted 34 bugs, of which 29 were confirmed as new: 21 schema-related logic bugs and 8 crashes, with no false positives~\cite[Table~2]{ddlcheck}. Seven of the 21 logic bugs never changed a query result. Four corrupted stored data and three corrupted the schema, so a SELECT-only oracle would not see them directly.

Table~\ref{tab:ddlstatements} shows which statement revealed each bug. SELECT reveals 23 of the 29, which fits the idea that a schema history creates a bad state and a later read exposes it. The other six are revealed by CREATE, ALTER, INSERT or REPLACE, and those are out of reach for any query-only comparison. The table names the statement that revealed each bug; the faulty component may lie elsewhere.

\subsection{Radar results}
Radar's ten rounds produced 1,663 bug reports. The authors spent about three weeks reducing them to 42 unique bugs, all submitted: 38 were confirmed as new (30 metadata-related, 8 other), one was a duplicate and three were false positives~\cite[Sec.~4.2]{radar}. The distribution is uneven. TiDB accounts for 31 of the 42 submissions and 24 of the 30 metadata bugs~\cite[Table~2]{radar}.

\begin{figure}[!tb]
\centering\includegraphics[width=\columnwidth]{fig5}
\caption{\textbf{Radar on TiDB with and without metadata guidance.} Cumulative unique bugs over 12 hours; each curve is flat after its last discovery. Re-plot of \cite[Fig.~7]{radar} from values read off the published figure; values are approximate.}
\label{fig:radarablation}
\end{figure}

The guidance ablation (Figure~\ref{fig:radarablation}) is the clearest single curve in the four papers. With guidance, Radar finds 19 unique bugs on TiDB in 12 hours; without it, 12, and the gap opens within the first two hours. Across all five DBMSs the totals are 22 against 14, and 19 of the 22 come from TiDB~\cite[Table~3]{radar}. Code coverage barely moves (20.3\% against 19.7\% of MySQL functions), another case where coverage misses an effect that bug counts show.

In the capability study, no earlier oracle exposes more than 13 of Radar's 30 metadata bugs (Figure~\ref{fig:homeset}). The fresh 12-hour run is stronger evidence, because every tool generates its own tests. All tools together find 21 metadata bugs, and Radar finds 20 of them, 15 that no other tool found (Table~\ref{tab:fresh}).

\begin{verdicts}
\verdict{\yes}{Raw-database comparison finds metadata bugs others miss.}{15 of 21 in a fresh run were found by Radar alone.}
\verdict{\half}{Guidance helps.}{22 against 14 unique bugs, but from one 12-hour run, and mostly on TiDB.}
\verdict{\half}{The method is general across DBMSs.}{24 of 30 metadata bugs come from one system.}
\end{verdicts}

\subsection{WriteCheck results}
WriteCheck's argument starts before any testing. In the 35 historical critical bugs, 32 (91.4\%) violate WSS, so a WSS oracle could in principle catch them~\cite{writecheck}. Of those 32, 29 trigger deterministically when the statements run in a fixed order, which justifies controlling statement order instead of relying on timing. The three that do not trigger show the limit of statement-level scheduling.

In discovery, WriteCheck flags 101 violations that group into 22 unique cases. Thirteen were confirmed as critical transaction bugs, 11 of them new, and nine were false positives. The nine of 22 describe the deduplicated candidates, not a false-positive rate over all executed tests, and reporting 101 bugs would overstate the result.

The tool comparison uses a \emph{different} set of 29 bugs, despite the identical count: the 13 critical bugs WriteCheck found plus 16 found earlier by DT\textsuperscript{2}, Troc and TxCheck~\cite[Sec.~6.5.1]{writecheck}. DT\textsuperscript{2} runs the same transactions on several DBMSs and compares them; Troc runs each transaction of a pair on its own view of the database; TxCheck builds equivalent test cases from statement dependencies. Replaying each bug's test case, WriteCheck exposes all 29, DT\textsuperscript{2} 23, TxCheck 16 and Troc 14, while the verification tools Elle, Cobra and Emme expose none. This set is the fairest of the four capability studies, because more than half of it comes from the competitors. In a fresh 12-hour run (Table~\ref{tab:fresh}), WriteCheck finds 4 critical bugs, the others 1 or 2. The others also find non-critical bugs, which WriteCheck by design cannot.

\section{Cross-study discussion and threats to validity}\label{sec:discussion}
The per-paper verdicts share a pattern: existence claims hold, size claims do not. Two reporting habits explain most of the gap, and both are easy to miss when reading one paper at a time.

\begin{figure*}[!tb]
\centering\includegraphics[width=\linewidth]{fig_homeset}
\caption{\textbf{Capability studies on known bugs.} Each panel takes one paper's bug set and shows the share that each tool can expose, as judged by that paper's authors. In the first three panels the set consists of the reviewed tool's own bugs, so it scores 100\% by construction. WriteCheck's set mixes its own 13 bugs with 16 found by the other tools. Sources: \cite[Table~2]{coddtest}, \cite[Table~4]{ddlcheck}, \cite[Table~5]{radar}, \cite[Table~3]{writecheck}.}
\label{fig:homeset}
\end{figure*}

\paragraph{Pattern 1: the home-set effect.} Figure~\ref{fig:homeset} lines up the four capability studies. Three of them ask how many of the \emph{new tool's own} bugs the older tools could have found. The new tool scores 100\% by construction, and the baselines can only lose. The design still answers a useful question, namely whether the new oracle reaches bugs the old ones cannot, and all four answer yes. It cannot answer the reverse question of what the new oracle misses that the old ones find. Only CODDTest's fresh SQLite run looks in that direction, and there CODDTest misses 14 bugs that other oracles found. WriteCheck's mixed set is the one design that partly corrects for this effect.

\paragraph{Pattern 2: headline counts sit at different stages.} Figure~\ref{fig:funnel} traces each campaign from raw reports to confirmed bugs of the targeted class. Every abstract leads with the second stage, but that stage means different things. CODDTest's 45 are all confirmed or fixed. WriteCheck's 22 are unique violations before confirmation, and only 11 survive as new critical bugs. Adding or ranking the headline numbers would mix these stages. Confirmation and fix counts are also snapshots at publication time, and the overlap between the four campaigns is unknown.

\paragraph{Internal and construct validity.} The main internal threat is a broken precondition: nondeterminism, errors, type conversion or an incomplete rebuild can make the two executions differ without any defect. Reduction can change the execution plan, so a reduced case needs re-checking. Developer confirmation helps, but projects apply different severity labels. On construct validity, a unique query plan is not necessarily a unique semantic path, high coverage coexists with undetected faults (SQLite reaches full branch coverage with its own test suite and still has logic bugs~\cite[Sec.~4.3]{coddtest}), and a fast tester can repeat equivalent cases. Bug counts also depend on how aggressively the authors reduced and deduplicated.

\paragraph{External validity.} The systems span embedded, traditional and distributed designs, but deployments differ even for the same system: WriteCheck tests a single-node CockroachDB, Radar a three-node cluster~\cite{writecheck,radar}. Small generated states do not cover long production histories or arbitrary application transactions. The concentration of Radar's and WriteCheck's findings in TiDB may reflect that system's maturity, the tools' fit to its SQL dialect, or both; the papers do not separate these explanations.

\paragraph{What stronger evidence would look like.} Pin shared DBMS revisions across tools. Keep capability studies and fresh runs separate, and build the capability set from bugs that no compared tool found. Repeat randomized runs with recorded seeds and report the spread. Measure manual triage time and time to the first confirmed bug. Add negative controls, cases that look inconsistent but are valid, to measure each oracle's precision directly.

\begin{takeaway}
The four papers establish that each oracle finds real bugs the others miss. None of them establishes by how much, because their experiments were not designed to compare tools on neutral ground.
\end{takeaway}

\section{Conclusions and research directions}\label{sec:conclusions}

\paragraph{Combining oracles.} Read together, the four papers suggest building a DBMS test campaign around independent sources of disagreement. Start from a valid database state and apply each oracle inside its supported workload: CODDTest for expression evaluation, DDLCheck for schema history, Radar for optional metadata, WriteCheck for write interleavings. Keep their verdicts separate, so that each failure stays attributable to one relation. Composition needs its own validity argument. An evolved schema from DDLCheck would give CODDTest an interesting starting state, but only after the tester has confirmed the state was built as intended. Removing a constraint before a WriteCheck run changes conflict behavior and can invalidate the serial reference.

\paragraph{Open questions.}
\begin{enumerate}[leftmargin=1.4em,itemsep=2pt,topsep=2pt]
\item \textbf{What should guide the generator?} The depth sweep, DDLCheck's filter and Radar's guidance all point the same way: syntactic size is a poor target, and novelty of schema structure or metadata pays off. A feedback signal built on new combinations of operators, metadata and state is plausible but untested against confirmed bugs.
\item \textbf{How can triage be made cheaper?} WriteCheck shows that isolation-level names do not pin down write semantics, and Radar shows how much reduction a raw campaign needs. Per-dialect profiles of which transformations are valid could cut both.
\item \textbf{What about faults shared by both executions?} Every reference here runs on the system under test. Combining relations may expose more failures than repeating one, but agreement across a finite set of checks cannot certify correctness.
\end{enumerate}

\paragraph{Conclusion.} Each of the four oracles makes a different part of database behavior testable by comparing two executions that must agree. Each comparison holds only under its precondition. Expression replacement needs a stable, faithful value. Schema reconstruction needs the final definition preserved. Metadata removal needs a query whose meaning survives the removal. Serial replay needs a conflict model that justifies the inferred order. Within those conditions, the evidence that each oracle finds real and otherwise-missed bugs is strong. The evidence for ranking them is not there yet, and the most useful next step for the field is an experiment designed to provide it.
