\section{Experimental study}\label{sec:experiments}
All four papers make a solid case that their oracles work in practice, yet the strength of their experimental backing varies sharply across claims. Below we summarize the shared setup, review each paper's key experiments and grade its claims using the symbols from Table~\ref{tab:coverage}: \yes\ for solid support, \half\ for directional or conditional evidence, and \no\ when the experiments do not back the claim.

\subsection{Setup, datasets and metrics}
\paragraph{Setup.} Table~\ref{tab:glance} summarizes the four setups. All four tools are written in Java: CODDTest, Radar and WriteCheck extend SQLancer, while DDLCheck is standalone. Where deployment is described, client-server engines run in Docker or from official binaries, with SQLite embedded. DDLCheck, Radar and WriteCheck used 8-core, 32\,GB hosts; CODDTest's efficiency study used a 64-core, 512\,GB server with 10 threads per configuration. Because engine versions, budgets and baselines vary across papers (and authors upgraded builds mid-campaign), raw counts across studies reflect setup as much as oracle quality. We therefore compare quantitative numbers strictly within each paper.

\paragraph{Datasets.} None of the papers uses a standard benchmark, and three rely solely on synthetic inputs: SQLancer tables and expressions in CODDTest, random DDL chains and DML in DDLCheck, typed tables with constraints and indexes in Radar, and small typed tables with up to five explicit and autocommit transactions in WriteCheck. Synthetic generation fits semantic testing well. Correctness depends on SQL rules rather than domain data, fuzzing reaches unusual type, NULL and constraint combinations, and tiny databases keep counterexamples short enough to reduce. The cost is that none of the experiments says how these tools behave on large production databases.

WriteCheck is the only paper grounded in real bug history. Its authors studied 140 transaction bugs filed from 2018 to 2022, identifying 35 critical bugs that leave wrong data behind, of which 32 (91.4\%) violate WSS~\cite{writecheck}. Those 32 real defects are strikingly small~\cite[Fig.~2]{writecheck}: all need at most two tables and five transactions, 97\% of their initial tables have at most five rows, and 72\% require a specific key, index or column constraint. Historical bugs thus validate the oracle and calibrate generator bounds, while synthetic fuzzing finds new defects. Confirmed bug sets in the capability studies below provide a second source of real data.

\paragraph{Metrics and methodology.} Unique confirmed bugs serve as the headline metric, since developer confirmation is the clearest proof a finding is real, though counts still depend on how strictly authors reduce and deduplicate reports. Cost is measured as tests or queries per unit time. Two diversity proxies also appear: unique query plans in CODDTest (motivated by prior work linking plan diversity to bugs) and unique schema structures in DDLCheck. Code coverage is reported too, yet reveals little here: SQLite's own test suite reaches 100\% branch coverage while still shipping logic bugs~\cite[Sec.~4.3]{coddtest}.

Baseline comparisons take two distinct forms. A \textbf{capability study} fixes a set of known bugs and asks whether each tool could expose them. A \textbf{fresh run} gives every tool the same wall-clock budget to generate its own tests and counts what each finds. None of the papers reports variance or confidence intervals: comparative runs and ablations are single trials, and Radar's ten and WriteCheck's five discovery rounds report only totals.

\subsection{CODDTest results}
CODDTest reports four series: an intermittent four-month campaign on five DBMSs; an oracle comparison combining a fresh run on SQLite 3.30.0, bug-age tracking and a manual detectability check; an efficiency benchmark against NoREC, TLP, DQE and two CODDTest variants; and a sweep over maximum expression depth. Default runs use depth 3, 24 hours and 10 threads.

Across five DBMSs, CODDTest found 45 new bugs, including 24 logic bugs (19 fixed and 5 verified at publication). In the authors' manual breakdown, 11 of those 24 involve constructs earlier oracles omit, such as subqueries, \texttt{ON} clauses and \texttt{CASE} expressions~\cite[Table~2]{coddtest}.

\begin{figure}[!tb]
\centering\includegraphics[width=\columnwidth]{fig4}
\caption{\textbf{Tests versus unique query plans in 24 hours} on SQLite 3.42.0.0, one point per mode, from \cite[Table~3]{coddtest}. Throughput and plans come from separate matched runs; branch coverage is 62--64\% except DQE (46.7\%).}
\label{fig:efficiency}
\end{figure}

Figure~\ref{fig:efficiency} shows the throughput-versus-diversity trade-off. Because each case runs at least three queries, CODDTest completes 4.20 times fewer tests than NoREC and 1.96 times fewer than TLP in 24 hours, yet reaches roughly 15 times more unique query plans. Branch coverage sits at 62--64\% for every variant except DQE and misses this 15-fold gap completely. CODDTest's standalone variants show the source: expression-only runs fastest among CODDTest modes (1.42 billion tests) yet hits just 7,399 plans, whereas subquery-only hits 2.76 million plans versus 2.58 million for the full mode. In Figure~\ref{fig:depth}, raising maximum depth from 1 to 15 pushes per-query time up 9.91 times, cuts throughput by 89.4\% and shrinks unique plans. The sweep measures runtime cost clearly, yet never tests whether deeper expressions find bugs shallow ones miss.

\begin{figure}[!tb]
\centering\includegraphics[width=\columnwidth]{fig_depth}
\caption{\textbf{Cost of CODDTest's expression-only mode as maximum expression depth increases,} one 24-hour run per depth, normalized to depth 1. Curves read from \cite[Figs.~2 and~3]{coddtest} (approximate); endpoint labels use the paper's reported values.}
\label{fig:depth}
\end{figure}

In the fresh 24-hour run on SQLite 3.30.0 (an older build where NoREC and TLP had already found 31 bugs), CODDTest found 25 unique bugs, trailing the 27 found by both NoREC and TLP, though it caught more exclusive bugs than any rival (4 versus 3 for NoREC and EET and 2 for TLP; Table~\ref{tab:fresh}).

\begin{verdicts}
\verdict{\yes}{CODDTest uncovers new logic bugs in mature engines.}{24 confirmed logic bugs across five DBMSs, 19 fixed.}
\verdict{\half}{It reaches bugs earlier oracles miss.}{The 11-of-24 count is measured on its own bugs (Figure~\ref{fig:homeset}); the fresh run shows complementarity, not superiority.}
\verdict{\no}{Deep expressions are unnecessary, as the authors suggest.}{The depth sweep measures cost, not bug yield per depth.}
\end{verdicts}

\subsection{DDLCheck results}
DDLCheck presents a 24-hour-per-DBMS campaign across six engines, an ablation of its schema-diversity filter, and a conceptual check of whether NoREC, Radar and DQP could catch its confirmed schema bugs. Its default of 5,000 statements per database pair came from a pilot that also tested 25,000 and 100,000.

The campaign submitted 34 reports and earned 29 confirmations (21 schema logic bugs and 8 crashes), with zero false positives, 4 duplicates and 9 fixes~\cite[Table~2]{ddlcheck}. Seven of the 21 logic bugs never altered a query result: four corrupted stored data and three corrupted the schema. Across all 29 confirmed bugs, \texttt{SELECT} revealed 23 while \texttt{CREATE} (2), \texttt{INSERT} (2), \texttt{ALTER} (1) and \texttt{REPLACE} (1) exposed six~\cite[Fig.~6]{ddlcheck}, putting them beyond read-only oracles. In the conceptual comparison, NoREC exposed 0 of the 21 schema bugs, Radar 13 and DQP 9. In the ablation, keeping only DDL sequences yielding unseen schema structures raised unique bugs from 5 (random selection) to 8 (Figure~\ref{fig:ablation}b); a stricter filter triggered the same 9 raw failures but only 4 unique bugs.

\begin{verdicts}
\verdict{\yes}{Schema history exposes defects query oracles miss.}{29 confirmed bugs, zero false positives and 7 invisible to query output.}
\verdict{\half}{The diversity filter improves discovery.}{8 unique bugs against 5, from one 24-hour run per DBMS.}
\verdict{\no}{Effective testing of PostgreSQL and SQLite.}{Zero bugs in 24 hours cannot separate bug-free engines from an unexercised search space.}
\end{verdicts}

\subsection{Radar results}
Radar reports ten 24-hour discovery rounds per DBMS on five systems, a 12-hour ablation of metadata-guided generation with function coverage, and a comparison against DQE, NoREC, TLP and MutaSQL combining conceptual analysis with a fresh 12-hour run (omitting MutaSQL, which is not public).

Ten rounds produced 1,663 raw reports. Roughly three weeks of manual reduction distilled them into 42 unique submissions: 38 confirmed (30 metadata-related, 8 other), 1 duplicate and 3 false positives~\cite[Sec.~4.2]{radar}. TiDB accounts for 31 of the 42 submissions and 24 of the 30 metadata bugs~\cite[Table~2]{radar}. Radar's guidance ablation (Figure~\ref{fig:ablation}a) is the cleanest controlled signal across all four papers: on TiDB, guided fuzzing separates within two hours and ends at 19 unique bugs versus 12. Across all five DBMSs the totals are 22 versus 14, so TiDB supplies most of the gain. Function coverage barely moves (20.3\% versus 19.7\% on MySQL; 19.7\% versus 19.3\% on MariaDB). In the fresh 12-hour run, all tools combined found 21 metadata bugs; Radar found 20, including 15 missed by every baseline.

(b) Total unique bugs with and without each design choice, from \cite[Table~3]{ddlcheck} and \cite[Table~3]{radar}. Each bar comes from a single run.}

\begin{verdicts}
\verdict{\yes}{Raw copies uncover metadata bugs other oracles miss.}{15 of 21 metadata bugs in the fresh run were found by Radar alone.}
\verdict{\half}{Metadata guidance improves detection.}{22 versus 14 bugs in a single run, mostly on TiDB.}
\verdict{\half}{Findings generalize evenly across DBMSs.}{24 of the 30 confirmed metadata bugs come from one system.}
\end{verdicts}

\subsection{WriteCheck results}
WriteCheck backs its oracle with the historical study of 35 critical bugs, a five-round campaign on six DBMSs, a capability comparison on 29 known bugs, and a fresh 12-hour run against DT\textsuperscript{2}, Troc and TxCheck.

The historical study anchors the design: 32 of 35 critical bugs (91.4\%) violate WSS, and 29 of those 32 (90.6\%) trigger deterministically under controlled statement order. Discovery flagged 101 WSS violations that reduced to 22 unique cases: 13 confirmed critical bugs (11 new, 2 known: 9 in TiDB, 3 in MariaDB, 1 in MySQL) and 9 false positives. One detail requires care: the capability study also evaluates 29 bugs, yet it is a \emph{different} set of 29, combining WriteCheck's 13 bugs with 16 found earlier by DT\textsuperscript{2}, Troc and TxCheck~\cite[Sec.~6.5.1]{writecheck}. WriteCheck detects all 29, versus 23 for DT\textsuperscript{2}, 16 for TxCheck, 14 for Troc and 0 for Elle, Cobra and Emme (Figure~\ref{fig:homeset}). Because most cases come from competing tools, this is the fairest capability study of the four. In the fresh 12-hour run (Table~\ref{tab:fresh}), WriteCheck found 4 critical bugs against 1 or 2 for each baseline, though rivals also catch non-critical bugs outside WriteCheck's scope.

\paragraph{What the experiments prove.} A clear divide runs through all four studies. Discovery campaigns show that each oracle finds real bugs maintainers confirm and fix, and capability studies show many of those bugs lie outside older oracles' reach. Claims about \emph{how much} better one tool is than another rest on thinner ground: fresh runs and ablations use single trials with small counts, CODDTest trails NoREC and TLP in raw SQLite totals, and code coverage fails to separate configurations whose plan diversity differs 15-fold.

\section{Cross-study discussion and threats to validity}\label{sec:discussion}
Each paper reads well on its own. Side by side, three reporting habits blur any direct ranking by bug count, and none stands out until all four papers are read together.

\paragraph{Capability studies on the tool's own bugs.} Three of the four capability studies take the new tool's discoveries and ask how many older tools could catch them (Figure~\ref{fig:homeset}), guaranteeing the new tool 100\% by construction. That proves the new oracle reaches fresh territory, yet leaves the mirror question untouched: what does the new tool miss? CODDTest's fresh SQLite run shows that side most clearly, missing 14 of 39 bugs found collectively, while Radar also missed 1 of 21 metadata bugs in its comparison.

\paragraph{Headline counts from different triage stages.} Figure~\ref{fig:units} draws each reported item as one square. Every abstract highlights its row total, yet those totals represent different stages: all 45 of CODDTest's bugs are confirmed, WriteCheck's 22 unique violations include 9 false positives and 2 known bugs, and Radar's 42 submissions include 1 duplicate and 3 false positives. Ranking abstracts mixes confirmed fixes with raw alarms. Confirmation counts are also frozen at submission, and overlap across the four campaigns is unchecked.

\paragraph{The uncounted labor of triage.} Every unique bug starts inside a pile of raw failures someone must reduce and deduplicate. Figure~\ref{fig:triage} aligns the reported ratios: in CODDTest's SQLite run, NoREC and TLP emitted over 3,500 raw reports per unique bug, CODDTest about 280 and EET under 3; Radar averaged around 40 reports per bug and three weeks of manual work, while WriteCheck averaged about 5. Those ratios span three orders of magnitude, yet only Radar reports how long triage took. Flooding engineers with thousands of duplicates per real bug carries a steep operational cost that headline counts hide.

\paragraph{Threats to validity.} Internal validity rests on precondition soundness: stray nondeterminism, implicit casts or incomplete catalog reconstruction trigger mismatches without any DBMS bug. Construct validity is limited because distinct query plans do not ensure distinct semantic paths, and 100\% branch coverage still coexists with logic bugs in SQLite~\cite[Sec.~4.3]{coddtest}. External validity faces three constraints: deployments differ even for one engine (single-node CockroachDB in WriteCheck versus a three-node cluster in Radar), small generated tables differ from long-lived production databases, and bug finds cluster unevenly. In Figure~\ref{fig:dbms}, only CODDTest spreads its bugs evenly across targets; DDLCheck clusters in MySQL and MariaDB, while Radar and WriteCheck concentrate in TiDB. Because none of the papers separates dialect fit, engineering effort and maturity, Figure~\ref{fig:dbms} does not rank DBMS reliability.

\section{Conclusions and research directions}\label{sec:conclusions}
Read together, these papers suggest a modular testing suite built from independent oracles: CODDTest for expressions, DDLCheck for schema history, Radar for metadata and WriteCheck for concurrent writes. Keeping them separate ties every failure to one invariant; chaining them, such as running CODDTest or Radar over DDLCheck schemas, needs its own soundness proof.

\paragraph{Open questions.}
\begin{enumerate}[leftmargin=1.3em,itemsep=1pt,topsep=2pt]
\item \textbf{What should steer generation?} CODDTest's depth sweep shows that deeper syntax drives up cost without measuring bug yield, while DDLCheck's schema filter and Radar's metadata guidance point to unseen schema structures and metadata combinations.
\item \textbf{How can triage get cheaper?} Isolation names leave write semantics underspecified, and Radar still costs weeks of reduction; per-dialect profiles of valid transforms and locks could cut both.
\item \textbf{How can shared faults be caught?} Every oracle here uses the DBMS as its own referee; self-consistency checks narrow where bugs hide, yet identical faults on both paths still pass.
\end{enumerate}

\paragraph{Toward a neutral comparison.} Answering the open comparative questions requires a shared protocol: pin common DBMS revisions, build a neutral bug suite from independent historical reports (extending WriteCheck's start), and run all tools under equal budgets across multiple seeded trials. Report unique bugs with variance, false positives, raw reports per bug and triage time; include negative controls (valid tricky cases) to test precision; and score each oracle only on its claimed failure classes (Table~\ref{tab:coverage}).

\paragraph{Closing thoughts.} Each system opens a distinct layer of DBMS behavior to automated testing by pairing two executions SQL semantics force to agree, and each rests on its precondition: stable evaluation for folding, a faithful catalog for reconstruction, metadata-agnostic queries for raw copies, and an obeyed conflict model for serial replay. Within those bounds, all four papers show convincingly that they catch bugs earlier oracles miss; comparing them under one neutral protocol is the clear next step.
